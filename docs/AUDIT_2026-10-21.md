# OBS AirPlay — Audit 2026-10-21

Targets:
- **macOS plugin v2.6.0** (tag `v2.6.0` = `563f805`, UxPlay fork tag `uxplay-obs-airplay-v2.6.0` = `f12a037` on upstream v1.73.7). This is the release shipped three days after the previous audit (`docs/AUDIT_2026-10-18.md`), so this pass looks for what that audit missed and what the v2.6.0 changes introduced. Items that audit closed were re-checked and are not repeated unless the fix is incomplete.
- **Windows 0.5.0 beta** (tag `windows-v0.5.0` = `6e1e4f6` on branch `claude/upbeat-meitner-zf2a2e`, branched from `563f805`): Part B.

How it was done: the release preset was configured, built and tested locally (zero compiler warnings; 29/29 CTest tests pass in 70 s); five independent reviewers read the fork's network surface, the updater and release pipeline, the media player, the plugin core and mirror path, and code quality/tests/build/docs; a sixth reviewed the Windows port. Every finding rated Medium or above was then re-read in the current source by the lead auditor; those are marked **[verified]**. The others are marked **[reviewed]** (read by one reviewer with quoted code) or **[plausible]**.

Line numbers are for the commits above and will drift.

---

## Executive summary

v2.6.0 is in good shape: the previous audit's fixes are real (request limits, plist pre-checks, non-blocking httpd, session binding, Ed25519 updates, flock, TLS verification were all re-traced), the build is warning-free, lock order is consistent, and the release pipeline checks itself. The new problems are concentrated in two places the previous audit did not reach:

1. **Upstream UxPlay parsers that take sender bytes without bounds** (Part A1). The HLS master-playlist "language" parser (`uxplay/lib/airplay_video.c`) has a heap overflow and a division by zero, both reachable by any LAN peer through `POST /play` + `POST /action` with no PIN. The mirror SPS/PPS packet parser reads signed lengths with no bounds check. These are upstream code the fork exposes; they should be fixed in the fork now and offered upstream.
2. **The "From any web address" media policy is not binding** (A1, A3): names are resolved once for the check and again by FFmpeg (DNS rebinding), a resolver error is treated as "allowed", and redirects are checked only after the request was sent. The default "Only from the sending device" mode is unaffected.

Beyond those: the fuzz targets the completion record says run in CI do not run in CI; the release job's dependency cache can be seeded from `main` by anyone with push access, bypassing the release approval; the audio re-timer has no jitter margin after it anchors on audio and no drift slewing; and a `stop()` during a DNS lookup can hang the AirPlay HTTP thread or OBS exit.

Counts after verification: Part A (macOS) Critical 2 · High 3 · Medium 14 · Low 30. Part B (Windows beta) High 3 · Medium 8 · Low 7.

**Windows 0.5.0 beta in one paragraph:** it will probably load and probably mirror; whether an iPhone sees it depends on Windows' own mDNS responder, which nothing has exercised against a real sender yet. Five small fixes (W-1, W-2, W-3, W-5, W-6) should land before testers get it, because each produces a failure that looks like "iOS does not accept Windows' records", the one question the beta exists to answer.

## Part A — macOS v2.6.0

### A1. Security: unauthenticated network surface (UxPlay fork)

All of A1 is reachable by any host on the LAN; the receiver has no PIN by default.

**NET-1 — Critical — Heap overflow writing a sender-controlled HLS `LANGUAGE` value into a 6-byte field [verified]**
`uxplay/lib/airplay_video.c:382` (`char code[6]` in `language_t`) and `:451`:
```c
strncpy(languages[i].code, ptr, end - ptr);   // end-ptr is the full quoted length, never capped
```
Path: `POST /play` with a `Content-Location` ending in `/master.m3u8`, then `POST /action` type `unhandledURLResponse` whose `FCUP_Response_Data` is a master playlist with one `#EXT-X-MEDIA:URI=…,DEFAULT=…,NAME="…",LANGUAGE="AAAA…",…YT-EXT-AUDIO-CONTENT-ID=…` line. The copy overflows into the calloc'd `languages` array with attacker-controlled bytes and length. Called from `http_handlers.h:1379`. The attacker owns the session (their own `/play`), so the 2.6.0 owner check does not apply. Upstream v1.73.7 has the identical code. Fix (S): bound the copy to `sizeof(code)-1` and reject longer codes.

**NET-2 — Critical — Division by zero (SIGFPE) on a master playlist with exactly one language entry [verified]**
`uxplay/lib/airplay_video.c:477`: `*language_count = count/copies;`. `copies` is counted by `for (i = 1; i < count; …)`, which never runs when `count == 1`, so `copies == 0`. Same delivery as NET-1 with one entry; OBS aborts. Fix (S): bail out when `copies == 0`.

**NET-4 — High — Mirror codec packet (type 0x01) SPS/PPS/VPS lengths are signed shorts with no bounds against `payload_size` [verified]**
`uxplay/lib/raop_rtp_mirror.c:777-780` (H.264) and `:702-740` (HEVC):
```c
short sps_size = byteutils_get_short_be(payload,6);
unsigned char *sequence_parameter_set = payload + 8;
short pps_size = byteutils_get_short_be(payload, sps_size + 9);
…
sps_pps_len = sps_size + pps_size + 8;  malloc; memcpy(sps_pps + 4, sequence_parameter_set, sps_size);
```
A value ≥ 0x8000 becomes negative: the PPS offset points before the buffer and the `memcpy` length becomes huge; small `payload_size` with the HEVC branch reads from `payload + 0x75` past the buffer. Type 0x01 payloads are not encrypted, so any peer that completes an RTSP SETUP (no PIN) and connects to the mirror port can send one. The fork hardened the adjacent encrypted-VCL loop (`:515`) but not this parse. Upstream code. Fix (M): treat the sizes as unsigned and require `offset + len <= payload_size` before each read; drop the packet otherwise.

**NET-3 — Medium — `assert`s validate sender HLS data and are compiled out under NDEBUG, leaving `languages[-1]` [verified]**
`airplay_video.c:520` `assert(i_default >= 0)` then `:547` `code = languages[i_default].code;`. Release builds define NDEBUG for the whole tree. A playlist whose languages contain no `DEFAULT=YES` and no match reads `languages[-1]`. `assert(count1 == count)` and `assert(length == strlen(data))` (`:459, :467`) likewise stop validating. Fix (S): replace each with a real check that returns the playlist unmodified.

**NET-5 — Medium — Media URL policy can be bypassed by DNS rebinding, fails open on resolver errors, and checks redirects after the request was sent [verified]**
Only in the opt-in "From any web address" mode. `src/media-url-policy.cpp:158-163`:
```c
const int error = getaddrinfo(host.c_str(), nullptr, &hints, &results);
if (error != 0 || !results) { … return ""; }     // "" means allowed
```
The policy resolves the name once; FFmpeg resolves it again for the connection and for every segment, and the connected peer is never checked. A name that answers a public address first and `127.0.0.1` next (TTL 0), or one that simply times out on the policy's query, gets FFmpeg to connect to loopback or link-local. `src/media-player.cpp:965-978` checks the redirect target only after `default_io_open` has connected and sent the GET. The fork's own check (`media_url_policy.h:168-213`) covers literal addresses only. Fix: fail closed on resolver errors (S); connect by the vetted address (rewrite the host to the chosen IP, keep the name in a `Host:` header and the TLS `verifyhost` option, both available in the release libavformat) (M); set `max_redirects` to 0 and follow redirects yourself, re-checking each hop (M).

**NET-6 — Low — Spool worker can be restarted after `spool_shutdown` and then freed under it [plausible]**
`uxplay/lib/raop.c` `raop_destroy` runs `spool_shutdown()` before `raop_stop_httpd()`; `spool_enqueue` (`http_handlers.h:378`) recreates the worker whenever `spool_thread_running` is false, so a `POST /action` serviced in that window starts a worker that is never joined before `MUTEX_DESTROY`. Fix (S): stop httpd first, or refuse to start once `spool_quit` is set.

Checked and solid: body limits and the 256 MiB budget (symmetric accounting); `plist_from_bin_checked` wired into every sender plist parse; `SO_RCVTIMEO`/`SO_SNDTIMEO`/`SO_NOSIGPIPE`, staged peek, partial-write loops, 60 s reaping; 400 on session mismatch and 403 for non-owners; the textual URL policy (userinfo, IPv6 zones, mapped/NAT64, short IPv4 forms, `.localhost`); the sender-hosted `/play` URL is rebuilt from the connection's peer address.

### A2. Security: updater, helper, release pipeline

**SC-1 — Medium — The release job restores a dependency cache that any push to `main` can seed, bypassing the release-environment approval [verified]**
`.github/workflows/ci.yml:105-112`: `actions/cache@v4` keyed by the hash of `scripts/build-macos-release-deps.sh`. A collaborator with push to `main` (but no approval rights) can save a prefix with a trojaned `libavcodec.dylib` under that key from a `main` commit; the next tag build hits the cache, skips the SHA-256-verified dependency build, and Ed25519-signs the result. The approver reviews the tag's source, not the cache. Fix (S): drop the cache from the gated job, or key it on `github.run_id`, or record per-file SHA-256 at build time and verify in `package-macos.sh` before vendoring.

**SC-2 — Low — "Which version is latest" is unsigned and signatures never expire [reviewed]**
`src/plugin-updater.mm:314-319`: the signed text binds name, version, size and digest, but not a time or a minimum version. Whoever controls the `releases/latest` response (account compromise, or a CA-trusted TLS interposer honoured by `NSURLSession sharedSession`) can pin users to an older signed release or freeze them. Code execution is not reachable this way. Fix (M): a signed `latest.json` with an `expires` field, or a `notBefore=` line in the signed text.

**SC-3 — Low — No cap on bytes actually received: `size` is checked after the full download; the API JSON is unbounded [reviewed]**
`plugin-updater.mm:556-567, 480-485`; `airplay-ble-discovery.mm:275-294`. An interposer can stream gigabytes into the user's temp folder or the helper's memory. Helper-only impact. Fix (S): a download delegate that cancels when `totalBytesWritten > asset.size`; cancel the API read past ~1 MiB.

**SC-4 — Low — Actions pinned by floating tag; the release job's checkout persists a write-capable token during third-party builds [verified]**
`ci.yml:20, 54, 75, 98, 107`. Fix (S): pin to commit SHAs; `persist-credentials: false` on every checkout (the `gh` step uses `GH_TOKEN` from env).

**SC-5 — Low — Release-dependency build uses a predictable `/tmp` path when `TMPDIR` is unset [plausible]**
`scripts/build-macos-release-deps.sh:12, 75-77`: `mkdir -p` succeeds on a directory another local user pre-created; sources are extracted (after a correct SHA-256 check) into it. Fix (S): `mktemp -d`, or default under `~/Library/Caches` like `PREFIX`.

**SC-6 — Low — The `.pkg` (root postinstall) ships outside the Ed25519 trust chain [reviewed]**
`scripts/package-macos.sh:514-523`. First-time installers rely on GitHub TLS plus a `SHA256SUMS` served from the same place. Fix (S): sign `SHA256SUMS` with the release key and document verification; (M) a Developer ID Installer identity.

**SC-7 — Low — Third-party notices understate what is linked into `libairplay.a` [verified]**
`THIRD_PARTY_NOTICES.md:29` lists UxPlay as one GPL-3.0 row; the statically linked sources also carry LGPL-2.1-or-later headers (shairplay and RPiPlay files) and `srp.c` is MIT (csrp, Tom Cocagne), whose notice must ship with binaries. Compatible with GPL-3.0-or-later; a notice gap, not a conflict. Fix (S): add `licenses/csrp-MIT.txt` and an LGPL row.

Checked and solid: the signature chain (`.sig` fetched first; name/version/size/sha256 bound; size and digest recomputed from disk; `codesign --verify --deep --strict`, identifier, exact version, arch, minimum OS; all re-run at install; strict base64 and key/signature lengths); transport (`https`, `github.com`, `/releases/download/` prefix, no query, no userinfo; no ATS exceptions); staging (0700, `lstat`, `flock` with `O_NOFOLLOW|O_CLOEXEC`, uid and inode re-check; `ditto` rewrites `../` entries so zip-slip is not reachable, tested); helper launch (`posix_spawn` of `/usr/bin/open`, `argc == 2`, PID-reuse detection); BLE advertises nothing identifying; CI `permissions: contents: read`, `pull_request` not `_target`, key written with `umask 077` and deleted; every script `set -euo pipefail` and shellchecked.

### A3. Memory safety, threading, correctness (plugin)

**MP-1 — Medium — `stop()` and OBS shutdown block for the whole of a DNS lookup; nothing interrupts it [verified]**
`src/media-url-policy.cpp:158` `getaddrinfo` runs on the media worker (and FFmpeg's own lookups inside every open); every `stop()` caller joins the worker (`media-player.cpp:770-772`). `stop()` is called from UxPlay's single HTTP thread on `/stop`, `/play` and teardown (`uxplay-integration.cpp:398, 428, 486`) and from `obs_module_unload` (`:1032`). With "From any web address" on and the resolver unreachable (VPN just dropped), one `/play` followed by `/stop` stalls every AirPlay request for the resolver's retry budget; quitting OBS meanwhile hangs the same way. Same class as the previous audit's MEM-2. Fix (M): resolve on a helper thread polled against `stop_requested`, then open by the resolved literal (which also removes FFmpeg's second lookup and closes NET-5).

**MP-2 — Medium — `AudioRetimer` has no jitter margin after an audio-first anchor and converts clock drift into periodic drops and gaps [verified arithmetic; impact needs a device]**
`src/audio-retimer.hpp:62-80`, `src/airplay-server.cpp:224-232`. `normalizeTimestamp` maps the first packet of whichever stream arrives first to `now`, so when audio anchors the clock (audio-only RAOP, or a re-anchor after `video_set_codec` → `resetStreamClock()`) the re-timer starts with zero lead. With `kLateNs = 20 ms`, a packet arriving 25 ms after its play-at time inside the 2 s startup window is **dropped** (a click), and after it opens a **gap** and leaves the timeline at lead = (jitter − 20 ms): a jitter buffer that grows only by inserting silence. In the ridden-over state (normal after the first RTP sync) the timeline free-runs on nominal durations, so 50 ppm sender/receiver drift (180 ms/h) is corrected only by a whole-packet drop every ~3.6 min (sender fast) or a ≥20 ms gap every ~7 min (sender slow); nothing slews. The unit tests (`unit-tests.cpp:447-618`) advance arrival and content in lock-step, never with jitter, a slow sender, or an audio-first anchor. The device test that validated the re-timer was video-first mirroring with sound, which is the case it handles well. Fix (M): restart at `now + margin` (≈40–60 ms) after an anchor or resync; in the startup window hold rather than drop packets late by less than `kJitterNs`; slew `m_next` by a few samples per packet toward a target lead with hysteresis; add tests with ±30 ms jitter, a 50 ppm slow sender over a simulated hour, and an audio-first anchor.
Note: libobs 32.0.4 `source_output_audio_data` re-computes `timing_adjust = os_time - in.timestamp` on every in-threshold packet for a source with both `async_unbuffered` and `async_decoupled` set (which `AirPlaySource` sets), so the lead the re-timer maintains may not be the delay OBS applies; measure before changing `kMaxLeadNs`.

**MP-3 — Medium — `hardware_errors`/`hardware` in `VideoOutput` are written from the worker and the presenter without synchronisation [verified]**
`src/media-player.cpp:1603, 1672-1683, 1802, 2189`. `noteHardwareError` runs on both threads; the presenter resets the counter to 0 while the worker increments it. Lost updates can keep the counter below 3 so the software fallback never triggers (frozen picture for the rest of the item) or trigger it from one error. Data race (UB, TSan report); the media smokes do not run under TSan in CI. Fix (S): `std::atomic`, or count on one thread only.

**MP-4 — Low — At unload the decode thread outlives `UxPlayIntegration`; the per-frame callback reads the global `shared_ptr` without the lock [verified]**
`src/plugin-main.cpp:537-541` (lambda reads `g_uxplay_integration` without `g_uxplay_mutex`) and `:601-615` (integration reset before `g_airplay_server->stop()` joins the decode thread). Quitting OBS mid-mirror with up to 60 queued payloads: each decoded frame runs the callback while the object is being destroyed. Fix (S): drain or stop the decode thread first; copy the pointer under the lock in the lambda.

**MP-5 — Low — Finite but huge sender positions reach `static_cast<int64_t>` (UB) and stick in `/playback-info` [reviewed]**
`src/media-player.cpp:715-716, 2006-2007` (play) and `:789-795, 1448-1449` (seek): only non-finite values are clamped; `/scrub 1e30` on an unknown-duration item saturates to `INT64_MAX` on arm64 (last keyframe, every frame discarded) and `INT64_MIN` on Intel, and `info.position = max(info.position, position)` (`:1388`) can never lower the reported position. Fix (S): clamp to the duration or a ceiling, convert with `llrint` on a clamped value.

**MP-6 — Low — A failed rename is invisible and `g_server_name` is committed before success [reviewed]**
`src/uxplay-integration.cpp:848-856` logs a warning and restores the old context but never calls `setLastError`; `plugin-main.cpp:189-206` has already stored the new name, so retyping it is rejected as "already the advertised name". Fix (S): return bool, surface the error, commit on success.

**MP-7 — Low — The over-long-name warning is not surfaced when it happens, and the edited source keeps the >63-byte name [reviewed]**
`plugin-main.cpp:355-366, 374`: `set_module_settings` sets `g_server_name_error` but triggers no panel refresh, and `show_module_settings_in_sources(settings, origin)` skips the origin. Fix (S): set `g_status_dirty` and write the accepted name back into the origin's settings.

**MP-8 — Low — PERF-12 incomplete: `releaseFrame()` releases the lock and retain but `m_frame` still owns the VideoToolbox buffer until the next decode [reviewed]**
`src/h264-decoder.cpp:287-302`; the comment at `airplay-server.cpp:434-437` promises otherwise. A still screen pins one pool surface. Fix (S): `av_frame_unref(m_frame)` in `releaseFrame()`.

**MP-9 — Low — A refused redirect is retried five times with backoff and reported five times [reviewed]**
`media-player.cpp:477-486, 502-518, 550-554`: `ResilientHttpIo::reopen` returns false on a policy-refused redirect and both callers loop `kMaxAttempts`: ~0.5 s of sleeps, five requests, five warnings and five Status-line refusals. Fix (S): tri-state return.

**MP-10 — Low — `hls_attribute` matches names as substrings [verified]**
`src/hls-playlist.cpp:40-56`: `attributes.find("BANDWIDTH=")` hits inside `AVERAGE-BANDWIDTH=` when it comes first (Apple's own example playlists), so variants are chosen by average rather than peak and the preflight disagrees with FFmpeg's `variant_bitrate`. Untested. Fix (S): split on commas outside quotes; add the case to `testHlsParse`.

**MP-11 — Low — Every keystroke in "Server Name" rewrites `settings.json`, syncs cfprefsd and rewrites every other source's settings [reviewed]**
`plugin-main.cpp:350-375` → `apply_module_runtime` → `CFPreferencesAppSynchronize`, `module_settings_save` (tmp+bak rename), `show_module_settings_in_sources`; only the mDNS re-registration is debounced. Fix (S): route through the existing debounce or save only when a non-name field changed.

**MP-12 — Low — The one call that can throw has no handler on a C thread [reviewed]**
`std::thread` construction in `MediaPlayer::Impl::play()` (`media-player.cpp:748`) is reached from UxPlay's C HTTP thread via `on_video_play`; a failure would `std::terminate`. The two existing `try/catch` blocks wrap C calls that cannot throw. Fix (S): catch in `play()`; `noexcept` on the callback lambdas; one sentence in DEVELOPMENT.md.

Checked and solid: lock order (video queue → `m_decoder_mutex` → `m_audio_decoder_mutex` → `m_sources_mutex`; `queue_mutex` → `state_mutex` in the player; leaves never held across calls out); `HeldLock` makes the state-mutex contract a type; `obs_data` and weak-source handling; frame lifetimes; NAL parsing bounds; `video_set_codec` once per stream; the negotiated-format audio reopen; the 24 h update gate; the previous audit's MEM-2/3/4/7, BUG-3/4/14, PERF-1/3/15, SEC-4 (TLS: the release FFmpeg verifies the hostname, confirmed) and SEC-13 fixes.

### A7. Build and CI

**BC-1 — Medium — The release FFmpeg is never exercised by a test [reviewed].** Releases link a custom FFmpeg built with `--disable-everything` and an allow-list (`scripts/build-macos-release-deps.sh:142-171`); every test binary links Homebrew's full build. ## Part B — Windows 0.5.0 beta

Target: tag `windows-v0.5.0` (`6e1e4f6`), the uxplay submodule at `f12a037` plus `windows/uxplay-patches/0001–0005` applied at build time. Built with MinGW-w64 (MSYS2 UCRT64) against `obs.dll` from OBS Studio 32.0.4; static FFmpeg 8.1.2 (D3D11VA, Schannel), libcrypto 3.6.3, libplist. The tag's CI run is green on all jobs and all 31 tests passed on `windows-2022`; the runner has no GPU, no Bonjour, no OBS UI and no AirPlay sender, and no test loads the finished DLL into any process. The release notes already say so. Findings marked **[verified]** were re-read in the patch or source by the lead auditor.

### Verdict

**Will it load in OBS? Probably yes.** The export set is exactly what libobs looks up, the `.def` is generated correctly for x64, imports are only Windows system DLLs plus `obs.dll` (checked by objdump in CI), every imported `obs_*`/`os_*` symbol predates OBS 28, and static libgcc/libstdc++/winpthreads inside a MinGW DLL sharing the UCRT with the host is a well-trodden configuration.

**Will an iPhone see it? This is the largest unknown, and the code has three High-severity problems around it.** With Bonjour installed *and running*, discovery is upstream UxPlay behaviour and should work. Without Bonjour the plugin registers through the Windows DNS Client service (`DnsServiceRegister`); the registration is correct in shape (instance and host names, TXT array, port byte order, string lifetimes), but a registration that fails asynchronously is reported as success and never surfaced (W-2), a machine with Bonjour installed but its service stopped gets no fallback (W-3), the de-registration path can free the service while a callback is outstanding (W-1), and the only test of this backend resolves from the same host, which Windows answers from its own table without touching the network (W-4), so iOS acceptance of the records is unproven.

**Will it mirror? Likely.** UxPlay's Winsock paths are upstream MSYS2 code, and D3D11VA goes through the standard `av_hwframe_transfer_data` copy with the existing software fallback.

**Most probable first breakages, in order:** Bonjour installed but stopped (dead discovery with only a warning); a Windows account with a non-ASCII user name (a new random MAC and public key every launch, so iOS sees a fresh receiver each time); the Windows mDNS responder's on-the-wire behaviour toward iOS; a crash on a quick rename or quit right after start.

So: it could work as is on a clean Windows 10/11 PC with an ASCII user name and no Bonjour, if Windows' responder answers iOS the way the API promises. It should not go to testers without W-1, W-2, W-3, W-5 and W-6, which are all small, because each would produce a confusing report that is hard to tell apart from "iOS does not accept Windows' records", the one thing the beta is meant to find out.

### Findings

**W-1 — High — De-registration reuses the single auto-reset event that registration also sets [verified]**
`windows/uxplay-patches/0002…patch`, `lib/dnssd_win32.c` lines 267–273 and 377–390 in the patch. `register_complete` and the de-registration callback both `SetEvent(service->completed)`; `native_deallocate` does `ResetEvent`, calls `service_deregister`, waits once, then `service_free(service)`. A registration completing during that wait satisfies it, and the service is freed while the de-registration callback is still outstanding (use-after-free inside OBS). Reachable by a rename within ~1–2 s of start (probing and announcing take about a second; the rename debounce is 0.8 s), by quitting OBS a second after launch, and by the start-failure paths that destroy a freshly registered context. Fix (S): count outstanding callbacks and free at zero, or use two events.

**W-2 — High — A registration that fails asynchronously is reported as success and never surfaced [verified]**
Patch lines 355–374: `native_register` sets `service->status = DNS_REQUEST_PENDING`, calls `DnsServiceRegister`, and returns `kDNSServiceErr_NoError` whenever the call itself returned `DNS_REQUEST_PENDING`. The outcome (name conflict, `EnableMDNS=0`, Dnscache not running, mDNS blocked by policy) lands in `service->status` and is never read or logged. `src/uxplay-integration.cpp:824–836` then logs "through Windows DNS service" and clears the panel error. Fix (S/M): wait up to ~3 s on both registrations and log the status; expose it so `UxPlayIntegration` can `setLastError`.

**W-3 — High — The backend is chosen by "does `dnssd.dll` load", not "is Bonjour running"; no fallback [verified]**
Patch, `lib/dnssd.c` lines 61–96: `LoadLibraryA("dnssd.dll")` succeeds whenever Bonjour (Apple Devices, iTunes, Bonjour Print Services) is installed; if the "Bonjour Service" is stopped or disabled, `DNSServiceRegister` returns `kDNSServiceErr_ServiceNotRunning` (-65563) and discovery is dead. `tests/dnssd-stub.c` reproduces exactly this path. Fix (S): query the service state (`QueryServiceStatusEx`) or `DNSServiceGetProperty(kDNSServiceProperty_DaemonVersion)` after loading, and fall back to the Windows backend when it fails. Also load with `LoadLibraryExW(…, LOAD_LIBRARY_SEARCH_SYSTEM32)` (W-13).

**W-4 — Medium — The CI test does not prove iOS can see the receiver [needs a PC and an iPhone]**
`tests/dnssd-native-smoke.cpp:91–117` resolves the registration from the same host with `DnsServiceResolve`; the Dnscache service answers from its own table. Probing and announcement, PTR answers to `_airplay._tcp.local` and `_raop._tcp.local`, SRV/TXT/A additionals and QU-query handling toward an Apple querier are untested. Fix (M): a Wireshark capture (`udp.port==5353`) while browsing from the iPhone; or a CI step that browses from a raw mDNS socket.

**W-5 — Medium — A receiver name containing a dot registers a malformed instance name [verified]**
Patch lines 295–299: `snprintf(instance_name, …, "%s.%s.%s", name, type, domain)` with no escaping; `DnsServiceConstructInstance` treats every `.` as a label separator, so "Studio 2.0" or "J. Smith's PC" produces a service iOS will not list. Bonjour's API escapes dots itself, so this is specific to the Windows backend. Fix (S): replace `.` in the name on Windows, or escape as `\.` and keep it only if it round-trips.

**W-6 — Medium — The MAC file and the software-decode flag are opened with the narrow CRT on a UTF-8 path [verified]**
`src/plugin-main.cpp:151, 176` (`fopen`) and `src/hardware-decode-option.hpp:33, 39` (`stat`). `obs_module_config_path()` returns UTF-8; MinGW's `fopen` interprets it in the ANSI code page. A user profile with Cyrillic, CJK or (on a mismatched code page) accented characters never reads or writes `mac_address.txt`, so `generateMACAddress()` gives a new MAC, a new RAOP instance name and a new `pk` on every OBS start: ghost receivers and re-pairing. `module-settings.cpp` and `updater.json` go through `obs_data_*` and are fine. Fix (S): `os_fopen` and `os_file_exists` from libobs `util/platform.h`.

**W-7 — Medium — `SO_REUSEADDR` on Windows lets the plugin bind TCP 7000 while another same-user process is listening there [verified: upstream code]**
`uxplay/lib/netutils.c:104–117`. The port-busy fallback to 7001 (`uxplay-integration.cpp:786–794`) never triggers; connections are split between the two listeners. Scenario: AirServer, 5KPlayer, LonelyScreen or a second OBS instance. Fix (S): `SO_EXCLUSIVEADDRUSE` under `_WIN32` (fork patch).

**W-8 — Medium — No wake mechanism on Windows: `httpd_wake()` is a no-op [verified]**
`uxplay/lib/wake_pipe.h:20–33, 45–54, 69`; `httpd.c:476–477`. `wake_pipe_open` leaves the descriptors at -1 under `_WIN32`, so the httpd thread's `select` runs its full 1 s timeout before `thread_tick`, and the audio and mirror threads fall back to a 5 ms poll (about 200 wake-ups per second while idle). A spooled Safari `blob:` video can start up to ~1 s late; `raop_stop_httpd()` and OBS quit wait up to 1 s. Fix (M): a bound loopback UDP socket pair as the wake descriptor.

**W-9 — Medium — `WinHttpSendRequest` is called with `WINHTTP_NO_ADDITIONAL_HEADERS` (NULL) and a header length of -1 [verified; outcome needs a PC]**
`src/windows-helper.cpp:199–205`. The API defines -1 only for a non-NULL header string. If Windows rejects the combination with `ERROR_INVALID_PARAMETER`, every `.sig` and installer download fails and the updater reports "the release signature could not be downloaded". Nothing in `tests/windows-update-tests.cpp` exercises the HTTP class. Fix (S): `headers ? (DWORD)-1L : 0`.

**W-10 — Medium — The elevated installer launch blocks the update thread that unload joins [verified]**
`src/windows-helper.cpp:511–512` uses `SEE_MASK_NOCLOSEPROCESS | SEE_MASK_NOASYNC` with `runas`; `:667` joins the thread in `stop_airplay_ble_helper()`, which `obs_module_unload` calls first. A user who clicks Install, sees the UAC prompt, and quits OBS instead hangs OBS until the prompt is answered or times out (about two minutes). Fix (S): drop `SEE_MASK_NOASYNC`/`NOCLOSEPROCESS` (the installer already waits on `/WAITPID`), or detach the thread when stopping mid-install.

**W-11 — Medium — No test ever loads `obs-airplay.dll` into a process [verified]**
The 31 tests link UxPlay, FFmpeg and OpenSSL statically into their own executables. Static-initialiser crashes, DllMain-time failures of static winpthreads or OpenSSL, or a missing import at the symbol level (objdump checks DLL names only) would show up only in OBS. Fix (S): a 30-line test that `SetDllDirectoryW(<obs bin\64bit>)`, `LoadLibraryW("obs-airplay.dll")`, calls `obs_module_ver` and expects 32.0.4.

**W-12 — Low — The installer finds OBS only in the 64-bit registry view** (`windows/installer/obs-airplay.iss:98–109`, `HKLM64\SOFTWARE\OBS Studio`); OBS's NSIS installer writes the 32-bit view unless `SetRegView 64`, so a custom-folder install gets no firewall rule and only an information box, suppressed under `/SILENT`. `diagnose.ps1:34` reads the same view. Fix (S): try `HKLM32` too.

**W-13 — Low — `LoadLibraryA("dnssd.dll")` uses the default search order** (OBS's `bin\64bit`, then CWD): any `dnssd.dll` next to `obs64.exe` is loaded into OBS. `dnsapi.dll` in the same patch already uses `LOAD_LIBRARY_SEARCH_SYSTEM32`. Fix (S): same flag.

**W-14 — Low — After a Winsock bind failure the log prints `strerror(errno)`** (`uxplay-integration.cpp:786–788, 798–799`), unrelated to `WSAGetLastError()`; the "port 7000 busy" diagnosis reads "No error". Fix (S): `WSAGetLastError` + `FormatMessage`.

**W-15 — Low — The hand-declared WinRT vtable for `IBluetoothLEAdvertisementPublisher`** matches the metadata order and IID, and CI exercised slots 0 and 2 on real Windows; `Stop` (slot 3) is reached only with a radio present. Windows may refuse an advertisement with no data sections; the loop would then log "off or not supported" every 30 s, harmless. Tester item.

**W-16 — Low — `obs_register_source` passes the 32.0.4 `sizeof(obs_source_info)`;** if OBS 30/31's struct is smaller, libobs refuses the source (DLL still loads). Not Windows-specific, but the Windows docs promise OBS 30+. Fix (S): check against the 30.0 header or say "OBS 32" in `docs/WINDOWS.md`.

**W-17 — Low — `diagnose.ps1:111–113`** enumerates every firewall rule's application filter (tens of seconds on Windows 11, looks like a hang); the `Resolve-DnsName _airplay._tcp.local -Type PTR` check (`:85–86`) is not guaranteed to be answered for the host's own registration without Bonjour's `dns-sd.exe`, so "was not seen" can be a false negative. Everything else (PowerShell 5.1 cmdlets, unprivileged `Get-NetFirewallRule`, ASCII without BOM) checks out.

**W-18 — Low — The `windows-beta-draft` CI job runs on every branch push** and, because `docs/releases/RELEASE_NOTES_windows-v0.5.0.md` exists on the tree, refreshes the `windows-v0.5.0` draft's target and assets from whichever branch pushed last, including macOS-only work. Harmless now that 0.5.0 is published; fix (S) before 0.5.1: restrict to the Windows branch.
